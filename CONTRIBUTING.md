# Contributing

This is about JSpice for Mac, under `macos/`. The Java project at the root (`src/`, `pom.xml`) is the original JSpice, built with `mvn clean package` and documented in [documentation/JAVA.md](documentation/JAVA.md); the Mac app uses none of it.

## Layout

`macos/Package.swift` is a Swift package (macOS 14, Swift tools 5.9) with these targets:

| Target | What it is |
| --- | --- |
| `CircuitKit` | the simulation engine and circuit model: parts, examples, boards, SPICE import and export, microcontrollers. No UI code, so it is unit tested on its own. Release builds skip Swift's run-time exclusivity checks here. |
| `CortexM4` | the ARM Cortex-M4 core (with its FPU) and the STM32 peripherals, in C, built with `-O2` even in debug builds. `stm32_pins.inc` is generated by `tools/arm-reference/pinmap.py`. |
| `JSpiceAutomation` | netlists, simulation runs, measurements, and the MCP server for AI agents |
| `jspice-mcp` | the MCP server on standard input and output (an executable) |
| `JSpiceAudioUnit` | the Audio Unit, an app extension inside the app |
| `JSpice` | the SwiftUI and AppKit app |
| `CircuitKitTests`, `JSpiceAutomationTests` | the tests; `CircuitKitTests/Fixtures` holds reference waveforms and firmware images |

Elsewhere in `macos/`: `Resources/` (Info.plists, entitlements), `scripts/` (`bundle.sh`, and profiling helpers), `tools/*-reference` (the reference tooling below) and `docs/` (the user documentation, starting from [macos/README.md](macos/README.md)). How the engine works is in [macos/docs/how-it-works.md](macos/docs/how-it-works.md).

## Build and test

Requires Xcode 15 or later. From `macos/`:

```
swift build                                      # debug build of every target
swift test                                       # the engine's and the automation's tests
swift test -c release -Xswiftc -enable-testing   # as CI runs them: audio-rate tests take minutes in a debug build
./scripts/bundle.sh                              # build/JSpice.app (Apple Silicon and Intel, signed ad hoc) and build/JSpice-macOS.zip
build/JSpice.app/Contents/MacOS/JSpice --self-test <folder>     # the interaction test, with screenshots of it
build/JSpice.app/Contents/MacOS/JSpice --screenshots <folder>   # a screenshot of each entry in Screenshots.swift's `shots`
```

Some tests skip unless what they need is there, as the fast CI lane runs them: `JSPICE_REQUIRE_TOOLCHAIN=1` requires the AVR and Pico toolchains (installed by Chip Support into Application Support), `JSPICE_MAKER_MODELS=1` downloads the makers' op-amp models and checks them against ngspice's figures, and `JSPICE_GRIDS_HEX`, `JSPICE_RINGS_HEX`, `JSPICE_PLAITS_HEX`, `JSPICE_TIDES2_HEX` and `JSPICE_BRAIDS_HEX` point at Mutable Instruments firmware built with `tools/arm-reference/build-mutable.sh` (GPL-3.0, so built where it is used, never kept here).

Other command-line modes: `JSpice --render-drawings <folder>` (drawings of the examples for schematic capture), `jspice-mcp --headless` (the MCP server without the app), `jspice-mcp --benchmark` (every example at 48 kHz), `jspice-mcp --benchmark-maker PART` and `jspice-mcp --capture-eval <folder>`.

## Continuous integration

Four workflows in `.github/workflows/`:

- **`macos.yml`, the fast lane**: on every push and pull request that touches `macos/**` (or the workflow), on any branch. The engine's tests that need no downloads (`swift test -c release`) and a build, beside a job that packages the app with `bundle.sh`, runs an MCP smoke test, validates the Audio Unit with `auval`, runs `JSpice --self-test` and `JSpice --screenshots`, and uploads the `JSpice-macOS` and `screenshots` artifacts. On a push, the screenshots are also published to the `ci/macos-screenshots` branch (`git fetch origin ci/macos-screenshots`, then `git show FETCH_HEAD:<name>.png`).
- **`macos-full.yml`, the full lane**: nightly (03:17 UTC), on demand, and on pushes to `master` touching `macos/**`, three jobs: the tests with the toolchains, firmware and makers' models they need; the benchmarks and profiles (informational, they cannot fail the run); and the schematic capture drawings, scored with `jspice-mcp --capture-eval` when the repository has an `ANTHROPIC_API_KEY` secret. A push to any other branch runs the firmware tests alone (the first job, `scope`, decides), and only when it touches what runs firmware: `Sources/CortexM4/`, the RP2040, STM32, AVR, GDB server, firmware loader, chip support, toolchain or microcontroller sources in `Sources/CircuitKit/`, or the workflow itself. It compares with the commit before the push, or for a branch's first push with where the branch left `master`. Without this, a change to an emulator on a branch would reach real firmware only after it was merged.
- **`release.yml`**: on a pushed `v*` tag, the fast lane's checks again, then a GitHub Release with `JSpice-<version>-macOS.zip` and its `.sha256` (see [Releases](#releases)).
- **`build.yml`**: the Java project, on Java 11, 17 and 21; not run for changes that touch only the Mac app.

## Releases

The version being built is in `macos/VERSION`, and `macos/CHANGELOG.md` collects changes under **Unreleased**. To cut a release:

1. Bump `macos/VERSION` (Semantic Versioning).
2. In `macos/CHANGELOG.md`, rename **Unreleased** to that version with the date (`## 1.1.0 - 2026-12-01`) and start a new empty **Unreleased**.
3. Commit, then push the tag `v<version>` (no workflow creates tags). The tag must match `macos/VERSION`; that version's changelog section becomes the release notes.

`release.yml` then builds, checks and publishes the release. With the Apple secrets named at the top of the workflow configured, the app is signed with a Developer ID and notarized; with the signing secrets alone it is signed but not notarized; without them it is the ad-hoc-signed build. The release notes say which, under the changelog's section, with the zip's SHA-256. A version with a hyphen (`1.2.0-beta.1`) is published as a pre-release. A manual run of the workflow (Actions ▸ release ▸ Run workflow, with a tag such as `v1.1.0`) is a dry run: the same build and checks, ending in a draft release and no tag; if the changelog has no section for that version yet, the draft's notes are the **Unreleased** section.

## Reference tools and fixtures

The engine and the emulators are checked against other simulators; the tools live in `macos/tools/`:

- **`spice-reference/`** (needs ngspice): `crosscheck.py` writes `Tests/CircuitKitTests/Fixtures/spice-reference.json`; `--ac`, `--devices` and `--netlists` write `spice-ac-reference.json`, `spice-device-reference.json` and `spice-netlist-reference.json`. Usage is in the script's docstring. `maker_models.py` (all models, or one: `python3 maker_models.py OPA1678`) prints ngspice's figures for each maker's model in the form of `MakerModelCatalog`'s `ngspice:` dictionaries, which `MakerModelCatalogTests` requires JSpice to match.
- **`avr-reference/`** ([README](macos/tools/avr-reference/README.md)): a Python model, a simavr tracer and a lockstep comparison; `build.py` compiles a sketch as JSpice does. The sketches the tests run are in `sketches/`, and `AVRTests.swift` holds them compiled; how the `avr-*.bin` fixtures were produced from them is not documented.
- **`pico-reference/`** (no README): `build.py` builds a sketch for the Pico as the app does (usage in its docstring; needs `PICO_CORE` and `PICO_GCC`), and `trace.ts` runs an image in rp2040js and prints the summary `PicoTests` reproduces (usage in its header comment). How the `pico-*.bin` fixtures were produced is not documented.
- **`arm-reference/`** ([README](macos/tools/arm-reference/README.md)): `fuzz.py` compares the Cortex-M4 core with QEMU's through Unicorn; `selftest/build.sh` builds `cm4-selftest.bin` and `stm32test/build.sh` builds `stm32-test.bin`; `stm32.py` runs a firmware on the STM32 model; `build-mutable.sh` builds a Mutable Instruments module's firmware; `pinmap.py` generates `Sources/CortexM4/stm32_pins.inc`.

## Extending the self-test

`JSpice --self-test` (`Sources/JSpice/InteractionTest.swift`) opens a window and works it as a person would: it draws a circuit with synthesized mouse events, moves, deletes, undoes, joins a part to a wire, turns a potentiometer and flips a switch, and checks the results. Each `Sources/JSpice/SelfTest*.swift` file adds one `extension InteractionTest` with a `static func check…() async` (`checkLayout`, `checkProblems`, `checkDiscovery`, `checkMenus`, `checkNotices`, `checkInspector`, `checkEditing`, `checkAccessibility`), called in turn from `InteractionTest.run`. Use `check(condition, "what should be true")` for each assertion and `await pause(seconds)` to let the UI settle; a failed check fails the run, and CI with it. To add screenshots, add a `Shot` to `shots` in `Screenshots.swift`.

Three things to know when adding a check:

- **Undo.** The run gives the editor an `UndoManager` of its own with `groupsByEvent` off, so that each action is one step as AppKit's per-event groups make it in the app: wrap what one user action does in `undo.beginUndoGrouping()` and `endUndoGrouping()`, as the run's `drag` does. Such a manager raises when an undo is registered outside a group, so `EditorState.registerUndo` opens a group of its own for an edit made outside one: that edit becomes a step of its own (in the app, whose manager groups by event, nothing changes). The editor holds its undo manager weakly: the run keeps the test's alive to the end (`withExtendedLifetime`), and a check that makes its own must keep it too, or its edits are not undoable at all.
- **The canvas is replaced.** Showing a board and coming back to the schematic gives the window a new `CircuitCanvasView`. A check that runs after one that shows a board must find the canvas again (`findCanvas(in: window.contentView)`) rather than use the one found at the start, which is no longer in a window: events sent to it go nowhere (no pointer for a paste, no value field).
- **Accessibility** is checked through the accessibility API (`checkAccessibility`), not with VoiceOver: see [macos/docs/accessibility.md](macos/docs/accessibility.md).

## Commits

Commit subjects are full prose sentences that say what the change does, without a trailing period, for example "Imports, exports and model downloads report through toasts over the canvas instead of dialogs, with long reports in a sheet to read and copy". Some older subjects start with an area (`CI:`, `STM32:`). When a change alters what the app does, update `macos/docs/` (and `macos/README.md` if the quick start or install change) in the same commit.
